# 管理员指南

[English](admin-guide.md) · [文档目录](README.zh-CN.md) · [升级指南](upgrading.zh-CN.md)

本指南用于首次部署和日常管理 Runmesh。默认部署在 Cloudflare Workers 上，Runner 安装在需要执行任务的 Linux、macOS 或 Windows 机器上。

部署后打开管理页面设置管理员密码，无需额外的初始化令牌。只有首个有效提交能成功，请在向不可信访问者开放前完成设置。新 Runner 默认使用受限服务账号（`dedicated_user`），新 MCP 客户端默认只有读取权限（`coding:read`），已有权限不自动修改。正式安装器使用已验证的签名发行物；使用新功能前，请核对[版本说明](release-notes.zh-CN.md)、[发行状态](release-readiness.md)和实例实际安装的版本。

## 部署前准备

准备以下内容：

- Cloudflare 账户和一个可访问的 Worker 域名；
- 一个只供管理员使用的强密码（至少 12 个字符）；
- 需要执行任务的机器；
- 明确哪些目录可以被哪些客户端读取、修改或执行命令。

受限模式的安装器会创建所需的服务身份，但不会替你决定工作区权限或修改项目目录的归属。请先规划最小权限。

新实例使用自己的资源。更新已有 v2 实例时，保留当前 Worker、命名空间、历史数据库、密钥值、Runner 配置和服务，不要为了更新代码重新建库或重新注册健康 Runner。早期版本的数据迁移说明不适用于普通升级。

## 部署控制平面

安装 Runner 前先查看[发布状态](release-readiness.md)。候选版本尚不是已发布正式包，其托管安装器可能有意保持不可用。请使用适合当前环境的发行物和安装流程。

在 Cloudflare Workers Builds 中连接仓库。正式环境必须使用签名发行物已验证并激活的 `main` 提交，当前 **0.1.4 候选版不能执行下面的生产部署命令**。候选版测试应选择 `dev`，使用独立资源和 `npm run deploy:worker -- --env development`，详见[部署参考](deployment.md)。

已经激活的正式版本在仓库根目录运行 `npm run build`，再执行：

```sh
npm run deploy:worker -- --env production
```

普通生产部署只需要两个独立的长期密钥：`INTERNAL_CONTROL_SECRET` 和 `RUNNER_TOKEN_PEPPER`。分别使用至少 32 字节的密码学安全随机数，更新时保留已有值，不提交到仓库、截图或日志。替换 `RUNNER_TOKEN_PEPPER` 会使已有 Runner 凭据失效，不能把重新生成密钥当作普通升级步骤。

普通生产部署无需额外填写明文运行时变量。Runmesh 校验公网 HTTPS 请求地址，默认使用配置的 D1 历史数据库，并在发行物通过所需验证后才提供签名安装器。反向代理使用内部 URL 时，可以显式配置 `RUNMESH_PUBLIC_ORIGIN`；转发头不能改变可信公网地址。`ADMIN_TOKEN` 仅供高级自动化管理 API 使用，网页管理、注册码和 MCP 不需要它。

`npm run setup:secrets -- --env production` 只检查缺失名称；加 `--apply` 才生成和上传缺失的必要密钥，不重新生成已有值、不打印密钥、不删除其他项。工具需要 Cloudflare 管理授权和已创建的 Worker。完整操作见[最小运行时配置](runtime-config.zh-CN.md)。

部署后立即完成管理员设置。单独的开发 Worker 选择 `dev`，使用独立密钥和资源，不复制生产凭据。

## 添加 Runner

1. 打开「Runner」页面，点击「添加 Runner」；
2. 输入便于识别的显示名称；
3. 选择执行模式。普通场景使用受限服务账号；只有确实需要时才使用高权限模式；
4. 阅读高权限警告并确认；
5. 生成一次性注册码；
6. 复制页面显示的操作系统命令，在目标机器上以管理员权限运行；
7. 返回页面确认 Runner 在线。

添加或重新安装 Runner 时，可以分别填写 Runner 授权和一次性注册码的有效天数。Runner 授权从保存时开始生效，填 `0` 表示永久有效；注册码立即生效且只能使用一次，重新生成会使旧注册码立即失效。不要把注册码写入脚本、工单或聊天记录。Runner 授权过期后，连接和心跳仍可用于恢复，但新的受保护操作会被拒绝；在控制台延长期限后会恢复。

### 安装方式

托管安装器可用时，页面会显示适合 Linux、macOS 或 Windows 的完整命令。命令会固定版本、校验签名、补齐运行环境、完成注册并安装守护服务。

托管安装器不可用时，请按[便携式安装流程](portable-runner-installation.md)先独立验证发布包，再执行 `runmesh enroll --code-stdin`。不要从 npm、分支构建或不明网址下载 Runner。

### 选择权限模式

- **受限服务账号**：适合长期运行。需要管理员明确把工作区目录授权给 Runmesh 服务账号。
- **高权限主机**：以 root、SYSTEM 或等效身份运行。只能用于完全信任的专用机器、虚拟机或容器。

`shell` 不是沙箱。即使工作区策略限制了文件路径，高权限系统账号仍可能访问整个主机。

## 配置工作区

在 Runner 详情页添加工作区：

1. 为工作区设置稳定的名称；
2. 选择绝对路径；
3. 分别勾选读取、修改、命令执行和任务控制；
4. 保存策略并等待 Runner 确认；
5. 使用 MCP 客户端调用 `workspace_list` 验证结果。

Runmesh 只把每个配置的工作区根路径发送给对应 Runner，并在 MCP 工作区和诊断元数据中省略它。文件内容和命令输出仍可能包含主机路径，分享前应检查。修改策略后，Runner 在确认新版本前会拒绝受保护操作。

## 创建 MCP 客户端

1. 打开「MCP 客户端」页面；
2. 输入清晰的标签，例如“团队测试”或“个人开发”；
3. 只勾选需要的能力：读取、修改、执行和任务控制；
4. 创建客户端并复制一次性 MCP 地址；
5. 通过安全渠道交给指定使用者。

地址只显示一次。怀疑泄露时，在客户端详情页轮换或撤销，不要尝试修改地址内容。客户端可以限制可使用的 Runner；多个客户端在同一 Runner 上看到的任务记录属于同一个管理实例。

## 日常运维

- **查看状态**：Dashboard 查看 Runner 在线状态、最近任务和客户端。
- **轮换凭据**：Runner 轮换会使旧凭据失效并断开旧连接；MCP 客户端轮换会生成新地址。
- **撤销 Runner**：阻止重新连接，但不会自动终止主机上已经启动的进程；需要在主机上单独停止进程。
- **删除 Runner**：移除控制平面的 Runner 记录、工作区与策略设置及客户端选择。它不会卸载主机服务、停止主机进程或删除本地文件与任务，也不保证清除另行保留的审计和历史数据。
- **彻底卸载**：托管分发可用时，注册页面的「移除 Runner」命令会独立下载维护程序，可清理旧版本或不完整的安装，不依赖旧 Runner 是否完好。它会删除本地任务历史，保留项目工作区。托管分发不可用时，页面显示的是本地 CLI 命令，应先按[卸载说明](runner-uninstall.md)确认已安装版本支持完整清理。在本机终端或 SSH 中执行；控制台记录需另行删除。
- **紧急锁定**：输入 Runner ID 后立即阻止新的受保护操作；随后按需要撤销凭据并检查主机进程。
- **修改管理员密码**：修改后所有已登录的管理会话失效。

## 备份与恢复

按当前部署支持的恢复流程保护控制平面数据，并备份 Runner 配置、任务元数据、保留日志、已验证安装包和服务清单。Runmesh 不提供应用内完整备份或自动回滚。

重启 Runner 前暂停新任务，等待活动与排队任务结束，并检查状态不明的恢复进程。记录服务实际使用的程序与版本，在独立环境演练恢复。按[升级指南](upgrading.zh-CN.md)操作，不要把重建命名空间、轮换密钥、清空状态或重新注册健康 Runner 当作普通升级步骤。

## 生产安全清单

- 使用 canonical HTTPS 域名并配置日志脱敏；
- 管理员密码与两个必要的独立 Worker 密钥分开保存；可选管理 API 令牌也单独保管；
- MCP 地址和注册码不进入日志、浏览器共享记录或工单；
- Runner 使用受限服务账号和最小工作区权限；
- 高权限模式只用于专用、可信主机；
- 定期检查在线 Runner、客户端列表和最近任务；
- 为凭据泄露、Runner 被盗和服务失联准备轮换与停机流程。

## 云端任务不记录与额度隔离

进入 **MCP Clients → 客户端详情 → Cloud Job history / 云端任务记录**，选择“新任务不记录”并保存。不记录新任务的云端快照及相关 Job 工具审计；本地任务元数据和输出保留，既有云端历史不删除，必要的鉴权和防重放数据仍保留。恢复记录后不回填此前未记录的任务。

操作未记录的任务时携带 `workspace_id`，并使用 0.1.1 或更新的 Runner；带工作区的在线任务列表直接读取 Runner。未记录任务不提供离线云端历史。D1 仅承接可选审计以隔离额度，不是无限额度或核心鉴权的替代。详见[额度隔离](quota-resilience.md)。

## 定时上传、手动读取与保留天数

Runner 详情默认不读取任务历史或审计。选择历史类型和最近 10/20/50/100 条后点击“加载 / 刷新”。日志默认仅读末尾 4 KiB，可选 1/4/16 KiB 和前后片段。

“任务记录与保留”可选关闭、定时合并、立即上传；间隔为 1/5/15/60 分钟，云端已结束任务保留 1/3/7/14/30/90 天。默认每五分钟上传、云端保留七天，本地按天删除默认关闭；开启必须单独确认，运行中、排队、取消中及状态未确认的恢复任务不删除。

云端只保存有上限的任务元数据，不上传完整日志。批量上传和本地按天清理需要兼容的组件，从 Runner 0.1.2 开始提供；已安装服务不会自动升级。详见[批量任务历史](batched-job-history.md)。

## 多客户端排队与语言显示

兼容队列功能的多个 MCP 客户端可同时提交任务。0.1.4 候选版默认执行并发为 2，已有显式设置保留，管理员可配置 1–64 个执行槽；旧安装包可能使用不同默认值，请检查实际生效配置。最多等待 32 个任务，每个客户端最多等待 8 个。客户端间轮流调度，客户端内先到先执行。排队立即返回任务 ID，启动前重新授权，可取消；进程重启后不会盲目重放。shell 请求设置 `queue: false` 时，满载立即返回。界面按所选语言显示，不翻译用户数据、命令和日志。详见[队列与界面约定](job-queue-and-localization.md)。

## 按任务变化上报历史

0.1.4 候选版的按变化上报需要兼容的 Worker 与 Runner。不记录的任务和普通日志读取不会开启可选上传；已确认且没有变化的快照不会在空闲时继续上传。心跳、鉴权和维护请求仍会发生。已发布的 0.1.3 安装包不包含这一行为，使用前请查看[版本说明](release-notes.zh-CN.md)和[历史上报说明](demand-job-history.zh-CN.md)。
