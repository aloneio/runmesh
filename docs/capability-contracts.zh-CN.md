# 能力契约与按需诊断

本批对应新版计划 **R01／R07 的一个实施阶段**，基线为开发提交 `b1b2dbed1a35e68322d678ba3f540cc114d5ed4a`。源码和测试完成不等于已部署生产、已发布签名安装包或宿主已刷新工具缓存。

## 统一定义，不扩大权限

共享协议的 `operations.ts` 统一已有 25 个受保护 RPC 的 scope、工作区权限、任务检查和只读返回前策略复查。协议枚举、Registry 授权适配、Runner 能力广告及只读完成检查使用同一来源。未知方法没有授权定义，原型属性名也不能误取得授权。

`mcp/actions.ts` 统一 24 个 Runner 子动作与 RPC 的映射。公开工具仍为 10 个。选择 Runner 和控制面查询保留原路径；每次调用继续重验客户端、工作区、策略、会话及任务权限。

## 分开报告能力与权限

现有 `inspect` 的 `diagnostics` 子动作仍只调用一次 `env.info`。新 Runner 附带严格、有界的能力报告，包括版本、方法集合、协议标识和并发上限。主机名、绝对路径、服务身份、凭据和环境变量不进入该报告。

| 字段 | 正确含义 |
| --- | --- |
| `runner_support` | 在线对端自报实现该方法，不表示操作系统访问和外部依赖均已验证 |
| `permission_snapshot` | 本次 scope 与有效权限的观测，不是之后可以复用的执行授权 |
| `requires_final_authorization` | 始终为 true，每次调用仍须通过最终检查 |
| `requires_job_check` | 该动作还需要已有的任务和工作区检查 |
| `host_catalog_state` | 固定 `not_observed`，服务端不假装看到宿主内部缓存 |

旧 Runner 未报告时显示 `not_reported`；格式无效或不支持时显示 `invalid`。两者的方法支持状态均为 `unknown`，不按版本号猜测。有效但不完整的方法列表可以明确表示不支持。指纹不一致不会自动升级、重注册或放宽权限。

报告是经过认证的对端观测，不是签名构建证明；目录指纹也不是源码提交。权限在观测之后仍可能变化，实际执行必须重新检查。

## 对照真实目录

`/health` 新增 `mcp_catalog`，包含目录摘要、工具名及数量、动作数量和操作契约摘要。每个 `tools/list` 条目的 `_meta["io.runmesh/catalog"]` 携带相同指纹，诊断带完整摘要。

指纹覆盖公开输入／输出 JSON Schema、说明、注解、scope 和动作映射，不覆盖源码、宿主缓存或 JSON Schema 无法表达的跨字段校验。端到端测试逐个比较真实工具列表，不只检查工具数量。

宿主可能缓存旧 Schema 或忽略元数据。服务端一致不能证明宿主已经刷新；应分别对照真实 tools/list 和宿主显示参数。只刷新相关连接器，不为此重新生成凭据。MCP 地址含秘密，不得发布完整地址、授权头或带凭据的抓包。

## 开销和兼容边界

摘要只在 Worker 实例加载时计算，不新增数据库读写、定时器或逐调用监控。健康接口不访问 Registry、Runner 或 D1。诊断没有增加原有 RPC 数量，也不创建任务／审计历史行；已有鉴权仍有成本。

Runner 复用缓存探测，不增加 shell 命令或状态写入。局部回归验证 100 次报告读取只有首次既有 8 次探测、不创建状态目录；报告小于 2 KiB，诊断样例小于 16 KiB。这不是账户总消耗为零的声明。

报告放在原本允许 JSON 内容的 env.info 结果中，没有扩大严格消息封装或迁移数据库。原 v0.1.3 包保持不可变，新报告需要以后的正式 Runner 发行。新 Worker 配旧 Runner 仍可连接，只将能力标为未知。
