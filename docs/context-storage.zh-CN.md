# Context 容量与清理

使用 `context` 查看工作区 Context 用量并清理选定的旧版本。`storage` 和 `prune` 属于 **0.1.4 候选版**功能，需要兼容的 Worker 和 Runner。已安装 v0.1.3 Runner 时，请先升级到包含这些动作的已验证发行包。

## 查看用量

调用 `context`，传入 `action=storage` 和 `workspace_id`。需要 `coding:read` 和工作区读取权限。结果包含版本数量与字节数、Context 数量、元数据字节数、各项限制、是否超额及未完成检查点状态。盘点只返回元数据；正文可通过独立的 read 动作读取。

每个工作区默认限制为：版本文件逻辑字节 **32 MiB**、版本文件 **4,096 个**、Context 目录 **256 个**。索引另有 **2 MiB** 限制，意图和临时文件有额外有界开销。规划主机容量时，还要计入其他工作区、Runner 数据和文件系统实际分配空间。嵌入式 ContextStore 可以降低这些限制。

超过上限的新检查点会被拒绝，已有数据保留。容量已满时，有效的重复请求仍可返回原回执。历史超额数据可继续定向读取；发现未知文件、链接或不安全目录时，需要管理员检查后再写入或盘点。

盘点扫描两层目录，最多 16,384 个目录项、8,192 个版本文件和 1,024 个目录，并在 I/O 操作之间检查四秒预算。超限返回 `context_scan_budget`；单次操作系统 I/O 可能超过这个检查期限。盘点和预览保持记录与索引不变，文件系统仍可能正常更新访问时间。

## 预览清理

预览和执行都需要 `coding:write` 与工作区编辑权限。先调用：

```json
{"action":"prune","workspace_id":"workspace","keep_days":30,"keep_revisions":2}
```

候选版本必须同时满足：记录中的 `updated_at_ms` 早于 `keep_days`，并且位于该 Context 最近 `keep_revisions` 个现存版本之外。每个 Context 的最新版本始终保留。参数只用于本次请求。

预览返回 `plan_hash`、符合条件及本批候选的数量与字节数、保留的 Context 数量和扫描统计。它会校验版本指纹、文件名及索引指向的最新版本。若有损坏或未完成检查点，应先处理该状态。

## 执行已审阅的清单

使用相同参数，增加 `apply=true`，并把预览的 `plan_hash` 填入 `expected_plan_hash`。每次最多删除 128 个版本，可用 `max_delete` 缩小批次。`has_more=true` 时，下一批需要重新预览并审阅。

清单绑定工作区、策略代次、参数和观察到的文件。执行时重新计算清单，并在每次删除前检查当前授权、文件身份及受保护的最新版本。文件、新检查点或策略发生变化后，需要生成新预览。

Prune 释放版本数量和字节容量，同时保留每个 Context 及其最新版本。达到 Context 数量上限时，请保留数据，由管理员另行安排归档或移除。

## 处理中断

删除逐个版本进行。`context_prune_partial` 表示部分候选文件可能已经移除：请重新盘点，再审阅新清单。已删除版本无法通过回滚或索引重建恢复。备份和快照应单独管理保留期；这里执行普通文件删除，不是存储介质安全擦除。

同一私有状态目录应由一个 Runner 管理。它的进程内协调以其他进程和主机管理员不会同时修改该状态为前提。

## 兼容与审计

Worker 会检查当前认证连接是否支持请求的 `context.storage` 或 `context.prune`。缺少支持时返回 `runner_upgrade_required` 和 `operation_state=not_started`，旧连接仍可使用。请安装已验证的兼容 Runner 后重新连接。现有 v1/v2 记录和 v1 索引保持兼容。

Context 调用保留元数据审计，独立于 Job 记录偏好。盘点和清理结果包含用量与操作元数据。无效的清理回执按结果未知处理，重试前应先检查状态。详见[调用恢复](mcp-agent-call-contract.md)。
