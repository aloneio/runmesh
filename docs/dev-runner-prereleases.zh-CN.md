# dev Runner 自动预发布

使用开发预发布在独立的开发主机上测试新功能。上游仓库的 GitHub 工作流 `Dev Runner Prerelease` 每收到 5 次进入该工作流的 dev 推送，就尝试一次预发布；只有验证和签名检查通过后才会公开。正式 `Release` 工作流只面向 main。发布安装包不会部署 Worker，也不会升级已安装的 Runner。

安装时使用开发 Worker 的管理员页面，并核对它提供的精确版本。当前源码是 **0.1.4 候选版本**，源码版本号不代表相应 stable 或 dev 包已经发布。分叉仓库需要配置自己的发行自动化和签名环境，上游工作流限制在原仓库运行。

## 计数与版本

专用工作流只监听 `push -> dev`，不设置路径过滤，不接受 PR、标签、手动或复用调用。它自己的 `github.run_number` 用作推送计数，第 5、10、15 次依次成为发行机会。一次推送包含多个 commit 仍只算一次；合并到 dev 算一次推送；镜像到 GitLab 不再重复计数。`run_attempt` 不计入，失败后使用 Actions 的 **Re-run jobs** 重跑，不给此工作流增加手动触发入口。

计数从该工作流首次运行开始，不回溯此前的推送。工作流禁用或跳过 CI 而没有创建运行的推送不计入。仓库管理员重建、改名或增加触发类型前，应检查计数迁移和现有标签，避免编号冲突。

到期时核对实际 main 版本、最新已公开且不可变的正式发行、已审阅的发行状态和经过签名认证的 manifest；同时要求所选 main 提交已包含在固定 dev 源码的祖先历史中。全部一致后才将 patch 加 1，后缀使用 `-dev.<批次序号>`，序号从 0 开始。例如正式基线为 `0.1.3` 时：

| 推送序号 | 计划开发版本 |
| --- | --- |
| 1–4 | 不发版，仅显示剩余次数 |
| 5 | `0.1.4-dev.0` |
| 10 | `0.1.4-dev.1` |
| 15 | `0.1.4-dev.2` |

main 为 `0.1.1` 时则从 `0.1.2-dev.0` 开始。批次序号在该工作流内全局递增，不因正式版本变化而重置：例如第 20 次推送前 main 已到 `0.1.4`，该批次为 `0.1.5-dev.3`。失败批次可能留下编号空档，不会为了补齐编号而发布未验证代码。

首轮把触发提交 SHA/tree、main SHA/版本、正式发行 ID、签名对应的源码提交、已审阅的 manifest SHA-256、推送序号、运行 ID、开发版本/标签和源码时间写入 schema-2 计划，并在构建/签名前保存为不可覆盖的 Actions 产物。重跑复用原计划，即便 main 已更新也不换版本。计划保留 90 天，缺失或过期时明确失败。旧 schema-1 计划仍可用于核验已经公开的历史发行，但不能授权新的发布。

## main 升级和过期批次

main 只改版本号、仍为候选状态、与最新正式发行不一致、尚未同步到 dev 或 manifest 签名不符，都会阻止新批次。公钥从固定 main 提交读取，不信任下载产物自带的公钥。正式附注标签、签名 manifest 的源码提交和 `release/release-state.json` 的提交/摘要必须一致。当前 main 快照与历史签名源码是不同身份，审阅过的历史维护不能改写签名所记录的原提交。

应通过正常审阅合并将 main 同步到 dev，发行任务不会自动合并或改写分支。仅 cherry-pick 或 squash 后文件相似，不自动通过保守的祖先关系校验；main 后续的新提交也需要包含在待发源码中。

签名前和草稿转公开前均重新观察正式基线。正式发行已经变化时，未公开的批次报 `dev_release_superseded`，不改编号、不覆盖标签或资产，也不转为公开。升级前已经上传的草稿仍保留为草稿。已经公开且不可变的发行改走只读核验：使用原源码的信任公钥及已验证构建产物比较，不重新签名；单独重跑发布任务时跳过重新签名与可变发布门禁。完整重跑工作流仍可能执行前面的源码/构建检查。

下载签名证据后还会重读 main 和 Latest，防止混合不同时间点的观察。最终发布前检查缩小并发窗口，但 GitHub 的分支读取与发布 API 不是一个原子事务，不能把这些检查描述成阻止外部同时修改 main 的分布式锁。发生冲突也不会删除或重写已有不可变发行。

准备新的**正式版**时，仍需审阅并同步根目录、各 workspace 和 lockfile 版本、源码固定安装器版本与公钥，以及 `state=candidate`、`release_branch=main` 且不带旧提交/摘要的发行状态。`scripts/stable-publication.mjs` 检查稳定版本、候选状态、安装器嵌入公钥与源码信任公钥一致。版本、文档、完整 CI、仓库所有者、main 精确提交与签名门禁继续保留。公开资产验证后，再通过既有审阅激活流程记录新的 released 提交和 manifest 摘要。开发预发布等待这一过程完成，不根据候选版本猜测已发布。

## 构建、验证与签名

源代码中的正式版本号保持不变。开发构建复用 Runner 的声明生成和打包器，只在忽略的构建输出和隔离暂存包中写入预发布版本。签名归档包含 `build-inputs.json`，记录固定计划。Git 标签与签名 manifest 对应真实源码提交；版本覆盖是明确的构建输入，不是未提交的源码修改。

对最终 `.tgz` 离线安装并执行既有真实 MCP→Worker→Runner 测试，包版本和 CLI 实际 `--version` 都必须等于计划版本。完整源码 CI 仍执行 Linux、Windows、macOS、LTS、浏览器和集成检查。发行验证使用独立运行 ID 的并发组，不会被后续普通 dev 推送取消。

Job 工作区绑定支持该开发通道中的兼容版本：`0.1.4-dev.0` 高于正式 `0.1.1`，而 `0.1.1-dev.0` 及更旧预览版不受支持。版本兼容不会绕过客户端、工作区、策略和实际 Job 身份检查。

开发预发布只在同一次运行要求的 GitHub 验证全部成功后签名，包括仓库验证、浏览器、Linux/Windows/macOS 原生 Runner 和维护中的 Node LTS 检查。GitLab `dev` 可以作为 GitHub `verify-all` 之后的镜像及部署触发源，但需要单独配置宿主同步程序，本工作流不执行镜像。GitLab SaaS 计算额度和 Cloudflare 外部提交状态不是 Runner 签名前置条件。stable/main 正式发布使用独立的跨提供商发布策略。

复用既有 `RELEASE_SIGNING_KEY`、`RELEASE_SIGNING_KEY_ID` 和受信公钥目录。私钥只交给发布任务的签名步骤。独立环境 `dev-release` 应仅允许 **dev 分支**，不要放宽原来 main-only 的 `release` 环境。

发布流程为：创建带私密项目 Git 身份的附注标签 → 创建 `prerelease=true`、`make_latest=false` 的草稿 → 上传既有格式的 9 项资产 → 下载并核验签名及实际字节 → 公开预发布 → 检查 `immutable=true` 并再次下载核验。正式 Latest 不改变。资产包含 portable `.tgz`、manifest、签名、签名描述、SHA256SUMS、公钥目录及许可通知。

## 失败恢复与测试安装

已有标签必须对应完全相同的源码和计划。已有草稿必须属于本批次；先比较已上传字节，匹配后只补缺失资产。不更新标签、不覆盖资产、不使用 `--clobber`。已经发布且校验通过的重跑只做读取核验，不再发布。冲突、畸形或不完整上传状态需要人工调查。

修复临时 CI、镜像、API 或环境问题后，可使用 **Re-run failed jobs**。发布任务读取构建任务保存的 attempt，而不是盲目使用重跑的新 attempt，因此复用成功构建时仍能取得原产物。完整重跑产生独立命名的构建产物。不同批次使用不同运行 ID 锁和版本号，避免共享等待队列淘汰中间批次。

预发布完成后即成为 development Worker 可消费的候选版本。`runmeshdev` 只发现标签符合 dev 版本契约、资产完整且 `immutable=true` 的 GitHub prerelease，并把安装器固定到该精确 tag；安装器仍使用内嵌的受信 Ed25519 公钥校验签名清单、channel、prerelease 标志、artifact URL 和校验和。发现失败时 development 安装入口关闭，绝不回退稳定版 Runner。production 仍固定到独立审核的 stable release。发布不会自动升级／重启已经连接的 Runner，也不会把 dev 提升到 main。

## 使用前核对预发布

确认发行已公开、不可变、标记为 prerelease，且带有完整签名资产。手动安装时，按[便携安装校验流程](portable-runner-installation.md)使用独立可信的公钥，核对包版本和安装后 CLI 版本均等于选定 dev 标签。CI 成功不能代替发行和主机安装结果。

## 开发安装器可用性

开发环境的发行描述、安装、维护下载和管理员页面使用同一份已验签 dev 版本选择。缓存新鲜期为 60 秒；从验签起最多一小时内可以继续使用，同时在后台刷新。刷新限时 20 秒，失败不会延长原有一小时期限；未来时间戳和过期缓存不会使用，不可用结果不缓存。

版本按 dev 序号排序，不按发布时间排序，延迟公开的旧包不会替代新版本。健康接口正常不等于安装可用；请核对发行描述和所用 POSIX／PowerShell 安装器中的精确版本。核验刚发布的安装包时，也要考虑上述缓存时间。
