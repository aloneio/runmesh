# dev Runner 自动预发布

GitHub 独立工作流 `Dev Runner Prerelease` 在每 5 次进入该工作流的 dev 推送后，触发一次**开发预发布**。既有 `Release` 工作流继续只负责 main 正式发行，不改为开发发行入口。发布开发包不会修改已部署 Worker、正式安装器指针、凭据、生产命名空间或当前安装的 Runner。

## 计数与版本

专用工作流只监听 `push -> dev`，不设置路径过滤，不接受 PR、标签、手动或复用调用。它自己的 `github.run_number` 用作推送计数，第 5、10、15 次依次成为发行机会。一次推送包含多个 commit 仍只算一次；合并到 dev 算一次推送；镜像到 GitLab 不再重复计数。`run_attempt` 不计入，失败后使用 Actions 的 **Re-run jobs** 重跑，不给此工作流增加手动触发入口。

计数从引入这份新工作流开始，不回溯之前的推送。工作流被禁用、使用 GitHub 跳过 CI 指令而根本没有创建运行的推送无法计入。不要未经迁移设计就重建、改名或增加其他触发类型，否则会改变计数含义。

到期时读取实际 main 提交中的正式版本，将 patch 加 1，后缀使用 `-dev.<批次序号>`，序号从 0 开始。例如 main 为 `0.1.3` 时：

| 推送序号 | 计划开发版本 |
| --- | --- |
| 1–4 | 不发版，仅显示剩余次数 |
| 5 | `0.1.4-dev.0` |
| 10 | `0.1.4-dev.1` |
| 15 | `0.1.4-dev.2` |

main 为 `0.1.1` 时则从 `0.1.2-dev.0` 开始。批次序号在该工作流内全局递增，不因正式版本变化而重置：例如第 20 次推送前 main 已到 `0.1.4`，该批次为 `0.1.5-dev.3`。失败批次可能留下编号空档，不会为了补齐编号而发布未验证代码。

首轮把触发提交 SHA/tree、main SHA/版本、推送序号、运行 ID、开发版本/标签和源码时间写入严格校验的计划，并在构建/签名前保存为不可覆盖的 Actions 产物。重跑复用原计划，即便 main 已更新也不换版本。计划保留 90 天，缺失或过期时明确失败，不重新猜测版本。

## 构建、验证与签名

源代码中的正式版本号保持不变。开发构建复用 Runner 的声明生成和打包器，只在忽略的构建输出和隔离暂存包中写入预发布版本。签名归档包含 `build-inputs.json`，记录固定计划。Git 标签与签名 manifest 对应真实源码提交；版本覆盖是明确的构建输入，不是未提交的源码修改。

对最终 `.tgz` 离线安装并执行既有真实 MCP→Worker→Runner 测试，包版本和 CLI 实际 `--version` 都必须等于计划版本。完整源码 CI 仍执行 Linux、Windows、macOS、LTS、浏览器和集成检查。发行验证使用独立运行 ID 的并发组，不会被后续普通 dev 推送取消。

既有 Job 工作区绑定的版本下限也正确识别该开发通道：`0.1.4-dev.0` 高于正式 `0.1.1`，而 `0.1.1-dev.0` 及更旧预览版仍被拒绝。版本兼容不会绕过客户端、工作区、策略和实际 Job 身份检查。

签名前还要求同一 SHA 的 GitLab dev push pipeline 中 `verify` 和 `browser` 均成功且不允许失败。最多观察 40 次、间隔 30 秒；失败、缺失或无法访问的证据都不会当作通过。本项目的 GitLab 镜像为私有，必须在 GitHub 的 `dev-release` 环境配置 `GITLAB_READ_API_TOKEN`，使用项目级 `read_api`、Reporter 权限令牌，不复制操作者的广泛管理令牌。缺少配置会明确失败，不退回匿名查询。GitHub 完整验证则是当前发行运行的显式前置复用工作流。

复用既有 `RELEASE_SIGNING_KEY`、`RELEASE_SIGNING_KEY_ID` 和受信公钥目录。私钥只交给发布任务的签名步骤。独立环境 `dev-release` 应仅允许 **dev 分支**，不要放宽原来 main-only 的 `release` 环境。

发布流程为：创建带私密项目 Git 身份的附注标签 → 创建 `prerelease=true`、`make_latest=false` 的草稿 → 上传既有格式的 9 项资产 → 下载并核验签名及实际字节 → 公开预发布 → 检查 `immutable=true` 并再次下载核验。正式 Latest 不改变。资产包含 portable `.tgz`、manifest、签名、签名描述、SHA256SUMS、公钥目录及许可通知。

## 失败恢复与测试安装

已有标签必须对应完全相同的源码和计划。已有草稿必须属于本批次；先比较已上传字节，匹配后只补缺失资产。不更新标签、不覆盖资产、不使用 `--clobber`。已经发布且校验通过的重跑只做读取核验，不再发布。冲突、畸形或不完整上传状态需要人工调查。

修复临时 CI、镜像、API 或环境问题后，可使用 **Re-run failed jobs**。发布任务读取构建任务保存的 attempt，而不是盲目使用重跑的新 attempt，因此复用成功构建时仍能取得原产物。完整重跑产生独立命名的构建产物。不同批次使用不同运行 ID 锁和版本号，避免共享等待队列淘汰中间批次。

预发布完成后可显式安装到开发环境测试；它不会自动升级或重启当前 Runner，不会把开发分支提升到 main，也不会改动正式安装入口。下载后必须用受信源码中的公钥校验，再按项目既有方式进行开发安装；执行权限与 Node 支持范围不因开发版而放宽。

## 解耦与证据

`policy.mjs` 负责纯计数、版本和计划规则；`plan.mjs` 观察源码/Actions 上下文；`build.mjs` 负责隔离打包；`verify-ci.mjs` 适配 GitLab 证据；`publisher.mjs` 管理可测试的发布状态转换；`github.mjs` 与 `publish.mjs` 承担网络和文件系统适配。共享打包、manifest 和签名实现继续复用，Runner/Worker 运行时代码不依赖这些自动化模块。

`test/dev-release.test.mjs` 已登记到双端既有 tooling 检查，覆盖计数、非法版本、计划绑定、正式发行隔离、运行时版本、API 故障、草稿续传、重复执行、标签/资产冲突、同提交 CI 及工作流权限依赖。真实签名、远端调度、GitLab 可用性和安装是否成功，仍以对应实际运行结果为准，不以本地模拟冒充已上线。
