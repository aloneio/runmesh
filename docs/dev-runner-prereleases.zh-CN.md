# 使用开发版 Runner 测试新功能

[English](dev-runner-prereleases.md) · [升级指南](upgrading.zh-CN.md)

在独立测试主机上使用开发版 Runner。安装前打开开发 Worker 的管理员页面，核对页面提供的版本。开发版下载使用已验证的预发布通道，当前生产版本见[发行状态](release-readiness.zh-CN.md)。

从开发面板复制安装命令，Runner 会注册到该开发 Worker；生产面板的命令使用正式发行物与生产地址。请分别在对应环境中安装。

测试主机安装开发面板提供的版本即可，重启服务前先完成或取消活动任务。自行发布开发通道的管理员可继续按下文配置自动化。

## 选择并验证安装包

开发 Worker 从已公开且不可变的 GitHub 预发布中，选择资产完整、签名已验证、与 Worker 协议兼容的安装包。安装器固定到该精确标签，使用内嵌的可信 Ed25519 公钥校验签名清单、通道、资产地址和摘要。手动安装时，按[便携包验证流程](portable-runner-installation.md)使用独立可信的公钥。

安装后核对包版本与 CLI `--version` 均等于选定标签，再验证 Runner 连接、策略确认和所需 MCP 操作。

Worker 通常在 60 秒后刷新版本选择，后台刷新期间可在验签后的一小时内继续提供原安装包。新版本发布后，请核对面板显示的版本；安装暂时不可用时，检查发布工作流，并在下一次刷新后重试。

版本按 dev 序号排序，延迟发布的旧批次会保留较新的已选版本。Worker 更新期间，可继续提供已验证且协议兼容的开发包，待新批次发布并验证后刷新选择。安装前核对页面显示的包版本及其更新内容。生产环境使用单独审核的正式发行物。

## 配置开发版发布自动化

维护中的 GitHub 工作流 `Dev Runner Prerelease` 在 `aloneio/runmesh` 运行，每收到第五次创建工作流运行的 dev 推送，就尝试发布。每次发布在该次运行中完成验证与签名。通过自己的仓库发布时，请配置对应的发布工作流和签名环境。

GitHub 环境 `dev-release` 仅允许 **dev 分支**，使用 `RELEASE_SIGNING_KEY`、`RELEASE_SIGNING_KEY_ID` 和源码中的公钥目录。正式 `release` 环境继续仅允许 main。私钥只交给发布任务的签名步骤。

工作流监听 dev 推送，以自身的 `github.run_number` 确定发行机会：

| 推送运行序号 | 正式基线已验证为 0.1.3 时 |
| --- | --- |
| 1–4 | 记录计数，等待下一次发行机会 |
| 5 | `0.1.4-dev.0` |
| 10 | `0.1.4-dev.1` |
| 15 | `0.1.4-dev.2` |

一次多提交推送或合并计一次。重跑复用运行序号，GitLab 镜像也保留这个 GitHub 计数。计数从创建工作流开始；禁用或跳过后没有产生运行的事件不计入。改名或重建工作流前，先检查现有标签和计数迁移。

批次序号跨正式版本继续增加：第 20 次运行前，已验证正式基线若变为 `0.1.4`，该批次就是 `0.1.5-dev.3`。失败批次可以留下版本空档。

## 准备源码基线

新批次会核对 main 版本、最新不可变正式发行、签名清单和经过审核的发行状态是否一致。所选 main 提交必须是固定 dev 源码的祖先；祖先检查失败时，通过审阅合并将 main 同步到 dev。

首次运行会保存包含源码提交、正式基线和目标版本的发布计划。Actions 将计划或暂缓结果保留 90 天，方便重跑时继续处理同一批次。记录缺失或过期时，先检查工作流和已有发布资产，再继续处理。

main 准备正式发行期间，到期的开发批次会记录为**暂缓**。正式发行完成验证和激活后，下一个到期的 dev 推送可规划新批次；重跑时保留原批次的决定。维护者发布正式版本时，可按[发布清单](maintainers/release-process.md)操作。

## 构建与发布

构建器在隔离目录中生成计划 dev 版本的包，并加入 `build-inputs.json` 供追溯。标签与签名清单记录实际源码提交。

最终归档会离线安装，并通过本地 MCP → Worker → Runner 测试。包元数据与实际 CLI 都须报告计划版本，同次运行还须通过仓库、浏览器、Linux/macOS/Windows 原生测试和维护中的 Node LTS 检查。

发布流程创建附注标签和预发布草稿，上传规定的签名资产，重新下载核对字节，再公开并检查不可变状态和签名。资产包含便携归档、清单、签名、SHA256SUMS、公钥目录和许可通知。正式 Latest 继续指向正式发行。

通过 GitLab 部署的实例，按[部署说明](deployment.md)配置同步程序和构建连接，让 Worker 在 dev 提交通过 GitHub `verify-all` 后更新。

## 恢复失败批次

| 情况 | 处理 |
| --- | --- |
| 临时 CI、API 或签名环境故障 | 修复原因后，在 Actions 使用 **Re-run failed jobs** |
| 发布任务重跑复用成功构建 | 任务读取该构建记录的 attempt 和原始产物 |
| 发布计划缺失或过期 | 保留工作流记录和发布资产，请维护者核对批次 |
| `dev_release_superseded` | 正式基线已变化；保留旧草稿，由后续批次采用新基线 |
| 已有标签、草稿或资产与计划冲突 | 停止发布，核对精确源码、计划和资产字节 |
| 已公开的不可变发行 | 重跑只读验证现有发行物 |

匹配的草稿可补齐缺失资产，已有标签和资产字节保持原样，已公开发行保持不可变。工作流在签名前和公开前重新检查正式基线；其他维护者同时提升 main 时，应协调维护窗口。

发布成功后，核对开发 Worker 选中的版本，在目标测试主机上安装，再完成[升级验收](upgrading.zh-CN.md)。
