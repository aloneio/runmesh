# Job 与 Context 的恢复边界

操作中断后，先用原 Job 或 Context 标识检查状态，再决定是否重试。连接超时不能证明 Runner 上没有发生操作。本页描述当前候选版行为；排查旧版本时，应以已安装 Runner 的能力为准。

## 启动与取消 Job

Runner 在创建进程前检查当前工作区策略。排队任务启动前还需要重新通过控制面授权。任务仍在等待时取消可以阻止启动；已经运行时，取消会尝试终止身份已确认的进程。

发出取消请求不代表进程一定停止。如果终止未能送达或进程身份不确定，请再次查询 Job。命令已经写入的文件或产生的外部效果不会因取消而撤销。

Runner 保存终态元数据后才发布最终结果，非零退出会保留真实退出码。如果终态元数据无法保存，在恢复能够确认并持久化结果前，状态仍不确定，不能当作执行成功。Runner 重启后无法还原未观察到的退出码，因此恢复的进程可能保持 `unknown`；尚未启动的排队任务会标记为中断，不会自动执行。

保存回执和创建操作系统进程是两个独立操作。启动结果不明确时，应查询原来的 `job_id` 和 `workspace_id`，不要只为取得回执而再启动一次命令。详见[MCP 调用恢复](mcp-agent-call-contract.md)。

## 读取日志

日志查询按受限大小分页，不会启动、取消或修改任务。空输出和输出不可用是不同状态。`log_unavailable` 可能表示文件尚未创建、已经移除或无法安全读取，不能据此认定任务没有运行。

命令结束后，内嵌 stdout／stderr 读取失败时，应保留实际 Job 标识、状态与退出码，只重试日志查询。不完整 UTF-8 末尾见[字节分页](byte-pagination.zh-CN.md)，快照与追加日志的一致性见[绑定游标](bound-cursors.zh-CN.md)。

## Context 检查点与恢复

检查点依次写入意图、不可变版本和派生索引，最后清除意图。中断可能留下未完成的检查点。普通读取不会自动修复或写入缺失状态；需要恢复时，显式调用 `context` 的 rebuild 动作。重建会校验已有记录，不会改写其正文。

重建有资源上限，可能拒绝损坏、不安全或超额状态。请保留相关状态供管理员检查，不要直接删除未知文件。重建不能恢复已被清理的版本。

## 删除旧 Context 版本

Prune 必须先预览，再使用返回的清单哈希显式执行。Runner 在删除前检查候选版本、受保护的最新版本、文件身份及当前权限。清单哈希不能替代授权。

旧版本逐个删除。中途停止时，已删除的版本不会回滚。遇到 `context_prune_partial`，请重新盘点并生成新预览，再决定是否继续执行。最新版本和索引会保留。这里是普通文件删除，不会清除备份，也不是存储介质安全擦除。详见[Context 容量与清理](context-storage.zh-CN.md)。

## 主机与存储条件

同一状态目录应由一个 Runner 管理，并保持私有访问权限。进程内串行化只能协调该 Runner 内部操作，不能约束其他独立写入进程，也不能抵御恶意主机管理员。工作区 shell 使用 Runner 的操作系统身份，不是操作系统沙箱。

Job 元数据和日志有数量、字节上限，可选的按天保留设置还会删除终态数据。云端历史是有限的近期快照，不是完整备份。需要长期保留的数据应另外备份。详见[任务记录与保留](batched-job-history.md)和[安全模型](security.md)。

源码模块职责见[模块化架构](architecture-remediation.zh-CN.md)。
