# 升级已有实例

[English](upgrading.md) · [文档目录](README.zh-CN.md)

本指南适用于已有的协议 v2 部署。更新代码不等于新建实例：不要为了升级重置 Durable Object 命名空间、替换 D1、轮换密钥、删除 Runner 配置或重新注册健康 Runner。[旧版本迁移](migration.md)仅在其中明确指出的旧数据边界确实适用时使用。

## 先确认要更新什么

| 组件 | 更新会改变什么 | 不会自动改变什么 |
| --- | --- | --- |
| Worker | 控制平面代码和服务器工具定义 | 已安装的 Runner 程序及主机服务 |
| 签名 Runner 安装包 | 对应主机选用的可执行程序 | 其他主机或生产 Worker |
| MCP 客户端工具目录 | 客户端缓存的工具定义 | 服务端代码、权限或凭据 |
| 发布发行物 | 可下载的固定版本资产 | 任何正在运行的实例 |

先读[版本说明](release-notes.zh-CN.md)。标注“尚未发布”的改进不在已有正式包中，即使源码中的版本号仍与旧包相同。不要用分支构建代替已验证正式包；开发预发布应在独立测试环境中使用。

## 变更生产环境前

记录 Worker 部署及源码身份、Runner 安装版本、服务实际可执行路径和客户端工具目录。每台主机使用服务真正调用的程序运行 `runmesh --version` 和 `runmesh doctor --json`；`PATH` 上另一份 CLI 可能并不是当前服务。诊断结果先检查脱敏，再对外提供。

妥善保存部署配置、Worker 密钥、控制平面数据、Runner 配置与状态、服务清单、已验证安装包及项目备份。Runmesh 不提供应用内完整备份或自动回滚，应使用对应存储和部署支持的恢复流程，并先在独立测试实例演练。

安排维护窗口。重启 Runner 前暂停提交新工作，等待排队、运行中任务结束，并处理恢复后为 `unknown` 或 `cancelling` 的任务。关闭浏览器或撤销访问不是停止进程。记录活动任务 ID，避免因调用结果不明而重复执行。

## 分步骤升级

1. **先演练。** 验证目标签名发行物，在不使用生产凭据或数据的环境中测试 Worker、Runner、服务账号和 MCP 客户端的组合。
2. **部署经过审核的 Worker。** 使用现有生产 `main` 部署路径，保留资源绑定和密钥值。`INTERNAL_CONTROL_SECRET` 与 `RUNNER_TOKEN_PEPPER` 保持独立；重新生成 pepper 会使已注册 Runner 凭据失效。详见[部署参考](deployment.md)。
3. **逐台明确升级 Runner。** 使用可信源码中的公钥验证目标包，按该版本适用的服务更新流程操作。保留既有配置、状态和上一份已验证安装包。不要删除当前安装来强行通过安装器检查。
4. **刷新 MCP 工具目录。** 服务端更新后，在各客户端刷新 Runmesh 连接与工具定义；刷新缓存不能补上旧 Runner 没有的能力。
5. **完成整条链路验收**后，再恢复日常任务。

[便携式安装示例](portable-runner-installation.md)用于首次安装，发现已有安装时会主动停止，并不是通用的原地升级器。目标版本没有提供适用于现有布局的流程时，应停下来由管理员制定并审核升级方案，不要临时拼接卸载清理、重新注册或手动切换链接等操作。

## 升级后的验收

确认 Worker 的版本和源码身份，再检查每台服务实际使用的程序与 `doctor --json`。确认 Runner 重连并确认工作区策略。通过真正要使用的 MCP 客户端检查所选 Runner、列出工作区、读取无害文件，并在获准的测试工作区执行无害命令。保存回执，按支持的工作区绑定约定查询同一个任务及其保留日志，同时验证一个预期的权限拒绝场景。

工作流依赖输入、取消、排队或云端历史设置时，使用受控任务分别验证。刷新客户端目录后检查动作是否与服务器一致。HTTP 健康检查、源码 CI 成功或安装包下载成功，都不能单独代替整条链路验收。

## 安全停止与恢复

签名、哈希、版本或源码身份不匹配时，在启用前停止。命令结果不明时先查询原任务，不要重新启动。服务或兼容性检查失败时保留日志和当前状态，只按已演练的恢复方案恢复相互兼容的程序、部署和状态组合。旧程序可能不理解新版状态或历史记录偏好。

不要通过删除命名空间、强制覆盖旧服务清单、恢复已泄露凭据或覆盖不可变发行物来让检查通过。凭据轮换及恢复注册仅用于已确认的凭据丢失、失效或撤销，不是普通升级步骤。
